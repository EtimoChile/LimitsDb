# Regulatory prompt: test authoring in LimitsDb

Use this document as a system instruction before generating or reviewing any
test in this project. Its purpose is to prevent implementation-coupled tests
that validate code instead of the specification.

---

## Problem this prompt prevents

Tests generated by reading the source code encode the current behavior as
correct behavior, including its bugs. A bug in the code produces a test that
always passes and protects the bug from being fixed.

The characteristic symptom is a test that can only fail if someone modifies
the implementation, never if someone introduces a regression in the specified
behavior.

---

## Authoritative sources of truth (read before writing any test)

In order of precedence:

1. `README.md` — public behavior, configuration, CLI, and operational flow
2. `limitsdb/resources/ilm.example.yml` — ILM policy contract and its
   invariants
3. `docs/configuration-contract.md` — configuration contract
4. `docs/exception-handling.md` — documented error contracts
5. Public module and class docstrings (not private function docstrings)

**Do not read the source code of the function under test before drafting the
test.** Read the specification first. Write the test. Only then verify that
the test is executable.

---

## Mandatory rules

### R1 — Name the behavior, not the function

The test name must describe an observable behavior in ILM domain terms, not
the function name or its internal mechanism.

```python
# FORBIDDEN — names the internal function
def test_build_dependency_graph_and_layers(): ...
def test_plan_mode_handles_empty(): ...
def test_normalize_and_duplicate_detection(): ...

# CORRECT — describes a domain behavior
def test_child_table_is_processed_after_its_parent(): ...
def test_plan_mode_reports_execution_order_without_connecting(): ...
def test_duplicate_table_in_ilm_file_is_rejected(): ...
```

### R2 — Do not call private functions directly

A function with a `_` prefix is an implementation detail. Changing it should
not break any test if the observable behavior is preserved.

```python
# FORBIDDEN — the test couples itself to the internal design
from limitsdb.core import ldb_runner
ldb_runner._build_dependency_graph(rows)
ldb_runner._compute_plan_layers(graph)
ldb_runner._plan_mode(config)

# CORRECT — invoke through the module's public interface or the CLI
from limitsdb.core.ldb_runner import run
result = run(config)
```

Valid exception: a private function that is the sole entry point to a
documented contract (e.g., a loading function whose error behavior is specified
in `docs/`). In that case document the exception with a comment citing the
source.

### R3 — Cite the specification source in each test

Each test must include a comment identifying which part of the specification it
is verifying.

```python
def test_child_table_is_processed_after_its_parent():
    # Spec: README.md > "Execution order" — child tables depend on parent rows
    # existing before their own ILM runs; a parent-child cycle is an error.
    ...
```

If there is no citable source for the behavior the test verifies, that test
should not exist or the specification must be updated first.

### R4 — Use explicit Given / When / Then structure in the body

```python
def test_table_with_no_eligible_rows_produces_skipped_result():
    # Spec: README.md > ldb-run exit codes — SKIPPED when there are no rows
    # eligible under the retention policy.

    # Given: policy with 3-month retention; all rows are recent
    config = ...
    engine = FakeEngine(rows=[])

    # When: the runner executes
    result = run(config, engine)

    # Then: the result is SKIPPED, not OK or ERROR
    assert result == RunResult.SKIPPED
```

### R5 — Forbid assertions on internal dictionary or type structure

```python
# FORBIDDEN — verifies the internal structure of the model
normalized_keys = set(ldb_ilm_config.IlmRule.__annotations__) - {"cond_expr"}
assert normalized_keys <= rows[0].keys()

# CORRECT — verifies observable behavior: the loaded rule can be executed
# and produces the documented effects
rule = load_rule(path)
assert rule.retain_months_source == 3
assert rule.is_active
```

### R6 — Generate at least one adversarial case per behavior

For each positive behavior, include at least one case that verifies what
happens when the input violates the documented precondition.

Adversarial case sources for this project:

- ILM policy with `retain_months_source: 0`
- Child table with `referencing_tables` pointing to a non-existent table
- Dependency cycle between tables (parent → child → parent)
- Empty ILM file or with `tables: []`
- Policy with `is_active: false` on all its conditions
- Unencrypted secrets when `enforce_encrypted_secrets` is `true`
- Worker failure on one table while another completes successfully

### R7 — Do not mock what can be built with controlled data

Mocking the function you are testing adds no information. Prefer fixtures
that represent real domain states.

```python
# FORBIDDEN — mocking the function being tested
monkeypatch.setattr(ldb_runner, "_load_offline_rows", lambda current: rows)
result = ldb_runner._plan_mode(config)  # only tests that the function calls the other

# CORRECT — build a real ILM file in tmp_path and use the public interface
ilm_path = tmp_path / "ilm.yml"
ilm_path.write_text(yaml.safe_dump({"tables": [...]}), encoding="utf-8")
config = Config(schema="s", mode="PLAN", ilm_config_file=str(ilm_path))
result = run(config)
assert result == 0
```

Valid exception: mocking the database layer (Oracle connections) is justified
in local tests because it requires external infrastructure. The
`DatabaseEngine` contracts are the mock specification.

## Pre-delivery checklist

Answer yes to each question before considering the test complete:

- [ ] Does the test name describe an ILM domain behavior?
- [ ] Is there a comment citing the specification source?
- [ ] Does the test invoke only public interfaces (except for a documented exception)?
- [ ] Do the assertions verify observable effects, not internal structure?
- [ ] Is there at least one adversarial case for this behavior?
- [ ] If the bug this test is meant to detect is introduced, does the test fail?

The last question is the most important. State it explicitly: *what change in
the code would make this test fail?* If the answer is "I don't know" or "no
reasonable one", the test is not measuring what it should.

## How to use this document

Include the content of this file at the start of any session or prompt
intended to generate or review tests in LimitsDb, before providing the source
code of the modules under test.

Before writing a new test, also consult [`docs/test-organization.md`](../test-organization.md)
to determine which file the test belongs in. The two documents are complementary:
this one defines **how** to write each test; that one defines **where** it lives.
