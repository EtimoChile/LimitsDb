# Open pending items

Compact queue. Each pending item must identify an owner artifact and a next
action. When resolved, remove it from this table and record any durable
decision that resulted in `DECISIONS.md`.

Allowed states: `OPEN`, `IN_PROGRESS`, `DEFERRED`, and `FUTURE`.

PEND-022 to PEND-026 are one concurrency/state design agreed on 2026-10-20. It
is described in `docs/concurrency-control.md`, which must be kept in sync with
the implementation (rules marked `[target]` become `[current]` as they land). The lock table,
`run_id` and mutex apply only to the runner modality; manual `SCRIPT` blocks
stay lock-less with the known gaps, because a `run_id` check would break them.

| ID | Status | Scope | Pending | Owner artifact | Next action |
|---|---|---|---|---|---|
| `PEND-022` | `OPEN` | ERROR persistence | A block that fails with an error other than `-20001/2/3/5` (e.g. `-20004`) writes the ERROR twice: the PL/SQL `exception when others` (`check_save_status(ERROR)`) and `process_table` through `engine.save_error_status`. Target: Python writes the ERROR only when `ldb_ctl` has no ERROR of this run yet (e.g. status ERROR with `ctl_process_end` later than the worker's `process_start`), so failures outside the block (compile error, missing procedure) are still recorded. | `limitsdb/core/ldb_runner.py` (`process_table`), `limitsdb/db/oracle/ldb_engine_impl.py` | Implement the conditional write with tests. |
| `PEND-023` | `OPEN` | Runner mutex per table | One lock row per table `(owner, table)` (not per runner: runners over different schemas coexist). Start: idempotent anchor rows (`INSERT … WHERE NOT EXISTS`, own commit, ignore `ORA-00001`, existing or locked rows are never touched); on a dedicated connection that never commits nor runs DDL, `SELECT … FOR UPDATE NOWAIT` per table in sorted order (`ORA-00054` = another runner alive: rollback, exit 1); with the lock held, a short separate connection publishes the key row (`run_id` uuid, mode, host, pid, start) and commits; then workers launch. Periodic trivial query on the lock connection against idle/network cut. Mode-agnostic: EXECUTE/PREVIEW against EXECUTE/PREVIEW follow the same rules. DDL and grants for the new table in bootstrap. | `limitsdb/core/ldb_runner.py` (`ldb_exec_ilm`, runner start), `limitsdb/db/oracle/ldb_engine_impl.py` (DDL, grants) | Implement mutex, key publication, liveness query and tests; document the mechanism. |
| `PEND-024` | `OPEN` | Block hardening | (a) `CHUNK_START` and `CHUNK_END` must raise when `check_save_status` leaves `-20001/2/3/5` (today the result is ignored and the worker keeps processing, so two workers can run the same table and duplicate history). (b) With the `ldb_ctl` row locked, `CHUNK_START` (and `TSTART`) verifies the worker's `run_id` against the key row; mismatch sets `-20005` (ownership lost). `-20005` is treated like `-20001/2/3`: the loser writes nothing to `ldb_ctl`, in `check_save_status`, in the block `exception`, and in `process_table` (`owned_by_other_run`). (c) LOB `SOURCE_ILM` path (no chunks): `LSTART` locks the row without commit before the long statement and `LEND`/`TEND` close it. Lock-less SCRIPT blocks carry no `run_id`, skip (b); (a) and (c) apply to both modalities, since they only use the `ldb_ctl` row lock. | `limitsdb/db/oracle/ldb_engine_impl.py` (`CHECK_SAVE_STATUS_PROC`, `generate_sql_block`), `limitsdb/core/ldb_runner.py` (`process_table`) | Implement with tests, including a lost-lock scenario. |
| `PEND-025` | `OPEN` | PREVIEW/EXECUTE states and `process_date` | PREVIEW states are the EXECUTE ones prefixed with `P`: `PTSTART`, `PCSTART`, `PCEND`, `PTEND`, `PERROR` (and `PLSTART`/`PLEND`); `PTEND` replaces `TPEND` (rename in `ldb_status.py`, runner, engine and tests). An EXECUTE can run over a PREVIEW that is not running; a PREVIEW cannot run for a `process_date` that has any EXECUTE status. Only an incomplete EXECUTE of the same `process_date` is continued by an EXECUTE (a PREVIEW never is: it deletes nothing, so it starts over): finished tables stay finished and `ctl_rows_processed` is kept, not reset at `TSTART`. The runner then needs the baseline read before `TSTART` (or returned by the block) to report this run's rows next to the date total and to keep the "ERROR without progress becomes SKIPPED" rule, which today compares against `prev_rows_processed = 0`. Anything else (another `process_date`, another mode, or a PREVIEW over its own incomplete PREVIEW) is not a continuation: `TSTART` restarts the table row (counter to 0) and first closes the abandoned run in `ldb_log` with status `ERROR` (abandoned EXECUTE) or `PERROR` (abandoned PREVIEW), `log_process_end` equal to the last `CEND` timestamp, the rows processed so far, and the message "Incomplete process closed by a later process"; this applies to an EXECUTE over a non-terminal PREVIEW (any date) and over a non-terminal EXECUTE of another date, and to a PREVIEW over a non-terminal PREVIEW (any date) or over a non-terminal EXECUTE of another date. Resuming a crashed run never skips guards (a restart within 5 s of the crash gets `-20002`). Confirmed: an EXECUTE with a greater `process_date` takes over the truncated work of a previous EXECUTE. The runner takes `process_date` from the database `SYSDATE` and offers no manual option (only a SCRIPT block can receive it through `&process_date`), so a new date smaller than the abandoned one is reachable only by a clock regression or an edited script; the rule does not depend on which date is greater: the `process_date` of the inconclusive process is closed and the table restarts with the new date. A PREVIEW rejected by an EXECUTE of the same date fails with `-20006`. All these control rules live in PL/SQL (`check_save_status` at `TSTART`, mode derived from the `P`-prefixed status), so they also hold for SCRIPT blocks run by hand (PEND-027); Python only reports and logs. When an EXECUTE resumes a table, the runner logs that the process was resumed and the rows processed previously (read from `ldb_ctl` before launching). | `limitsdb/core/ldb_status.py`, `limitsdb/db/oracle/ldb_engine_impl.py` (`check_save_status`, `get_status`, `check_referencing_tables`), `limitsdb/core/ldb_runner.py` (`process_tables_cnf`, `process_table`) | Implement with tests and record the rules in `DECISIONS.md`. |
| `PEND-026` | `DEFERRED` | Lock-less SCRIPT blocks: guard gaps | The `TSTART` guard compares against `ctl_process_start`, which `CHUNK_END` does not refresh, so a block run by hand (lock-less modality: no runner mutex, no `run_id`) has a microsecond window between chunks, accepted as a known gap. Candidate: compare against `NVL(ctl_process_end, ctl_process_start)` and restrict it to transitional statuses (an ERROR retry within 5 s would otherwise fail with `-20002`). | `limitsdb/db/oracle/ldb_engine_impl.py` (`CHECK_SAVE_STATUS_PROC`) | Decide after PEND-023/024 are in place. |
| `PEND-027` | `OPEN` | SCRIPT mode parameter | A generated SCRIPT hardcodes the mode (`l_mode := '{execution.mode}'`) and Python decides at generation time whether the DML is emitted, the `check_referencing_tables` preview flag and the final status (`TEND`/`TPEND`). Target: the mode is a SQL*Plus substitution variable (e.g. `&ldb_mode`) validated in the block, and those decisions move to run time from `l_mode` (`if l_mode = 'EXECUTE' then` around the DML). Decided: SCRIPT supports both PREVIEW and EXECUTE, so the PREVIEW/EXECUTE control of PEND-025 (P-prefixed statuses, `-20006`, closure log row, continuation) must live in PL/SQL, not in Python; the block derives the status prefix from `l_mode`, rejects other values, and the generated text no longer depends on the mode. | `limitsdb/db/oracle/ldb_engine_impl.py` (`generate_sql_block`) | Implement together with PEND-025, with tests and SCRIPT docs. Normalize the SCRIPT substitution variables to the `ldb_` prefix used by the bootstrap (`&ldb_ts`, `&ldb_user_pwd_N`, `&ldb_link_pwd_N`): `&process_date` becomes `&ldb_process_date` and the new mode variable is `&ldb_mode`. |
